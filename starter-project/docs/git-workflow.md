# Git workflow для лабораторного практикуму

Цей короткий довідник описує лише ті операції Git, які потрібні для лабораторних робіт з дисципліни «Прикладні технології програмування в інформаційній безпеці». Його мета — забезпечити відтворювану історію роботи та зберегти докази станів «до виправлення» і «після виправлення».

## 1. Очікуваний результат

Після опрацювання довідника студент повинен уміти:

- клонувати приватний навчальний репозиторій;
- створити окрему гілку лабораторної роботи;
- перевірити зміни перед commit;
- створити змістовні commits;
- зберегти окремі commits уразливого та виправленого станів;
- створити й перевірити фінальний тег роботи;
- передати викладачеві точні назви гілки, тегу та commit hash;
- не додавати до Git секрети, локальні конфігурації та службові файли.

## 2. Одноразове налаштування

Перевірте інсталяцію Git:

```bash
git --version
```

Налаштуйте ім’я та університетську електронну адресу, якщо цього ще не зроблено:

```bash
git config --global user.name "Ім'я Прізвище"
git config --global user.email "student@example.edu"
```

Не записуйте до Git config пароль, access token або інший секрет. Спосіб автентифікації до університетського Git-сервера задає викладач або адміністратор сервера.

## 3. Початок лабораторної роботи

Клонуйте репозиторій один раз:

```bash
git clone <repository-url>
cd <repository-directory>
```

Перед новою роботою перейдіть до погодженої базової гілки та отримайте зміни:

```bash
git switch main
git pull --ff-only
```

Створіть робочу гілку. Для ЛР 1:

```bash
git switch -c lab/1-system
```

Для наступних робіт використовуйте назви з методички: `lab/2-input-sqli`, `lab/3-authentication`, `lab/4-authorization`, `lab/5-browser-xss`, `lab/6-hardening-review`.

Команда `git pull --ff-only` зупиняється, якщо історії розійшлися. У такій ситуації не запускайте навмання `push --force`, `reset --hard` або складний rebase: збережіть вивід `git status` і зверніться на консультації.

## 4. Щоденний безпечний цикл

Перед зміною коду перевірте стан:

```bash
git status
```

Після невеликого завершеного кроку перегляньте зміни:

```bash
git diff
git diff --staged
```

Додавайте лише перевірені файли:

```bash
git add path/to/file
git status
```

Після build і релевантних тестів створіть commit:

```bash
git commit -m "Implement server-side validation for create request"
```

Повідомлення має називати завершену зміну. Повідомлення `fix`, `lab`, `changes` або `final final` не допомагають відновити логіку роботи.

## 5. Стани «до» і «після» виправлення

Для SQLi, IDOR/BOLA, XSS та інших навчальних дефектів потрібні два різні commits.

1. Відтворіть дефект лише в дозволеному локальному середовищі.
2. Зафіксуйте мінімальний уразливий стан:

```bash
git add path/to/relevant/files
git commit -m "Reproduce controlled SQL injection scenario"
git rev-parse HEAD
```

3. Збережіть отриманий commit hash у звіті.
4. Виправте першопричину, повторіть початковий PoC і позитивний сценарій.
5. Запустіть релевантні тести.
6. Створіть окремий commit виправлення:

```bash
git add path/to/relevant/files
git commit -m "Parameterize search query and add regression test"
git rev-parse HEAD
```

Не переписуйте історію так, щоб уразливий commit зник. Водночас фінальна гілка та фінальний тег повинні вказувати на виправлений, а не на уразливий стан.

## 6. Перевірка секретів перед commit

`git status` і `git diff --staged` потрібно переглядати перед кожним commit. Не додавайте:

- `.env` з фактичними значеннями;
- паролі БД;
- cookies і access tokens;
- signing keys, API keys і private keys;
- локальні дампи БД;
- журнали з credentials;
- IDE- та build-артефакти, вже зазначені в `.gitignore`.

Перевірте staged changes:

```bash
git diff --staged
```

Якщо секрет уже потрапив до commit, простого видалення з наступного commit недостатньо: значення залишається в історії. Не публікуйте його повторно, повідомте викладача й дійте за наданою процедурою ротації та очищення історії.

## 7. Фінальний тег лабораторної роботи

Спочатку переконайтеся, що проєкт збирається, тести проходять, а робоче дерево чисте:

```bash
git status
git log --oneline -5
```

Створіть annotated tag, наприклад для ЛР 2:

```bash
git tag -a v0.2.0 -m "Laboratory work 2 completed"
```

Перевірте, на який commit він указує:

```bash
git show --no-patch v0.2.0
```

Надішліть гілку і тег до приватного remote:

```bash
git push -u origin lab/2-input-sqli
git push origin v0.2.0
```

Не переміщуйте прийнятий тег без погодження з викладачем. Виправлення після захисту оформлюється окремим commit і за правилами, оголошеними для потоку.

## 8. Команди для самоперевірки

```bash
git status
git branch --show-current
git log --oneline --decorate -10
git tag --list
git show --no-patch <tag>
git rev-parse HEAD
git diff <vulnerable-commit>..<fixed-commit>
```

Ці команди не змінюють історію. Вони допомагають відповісти на захисті: у якій гілці виконано роботу, де стан «до», де виправлення та який commit оцінюється.

## 9. Типові помилки

- уся робота виконана одним commit без відокремлення security-сценарію;
- фінальний тег указує на стан до виправлення;
- у звіті наведено commit hash, якого немає в переданому репозиторії;
- до commit додано `.env`, token або дамп БД;
- використано `push --force`, і доказовий commit зник;
- студент працював без окремої гілки й змішав кілька лабораторних;
- код змінено після запуску тестів, але перед створенням тегу тести не повторено;
- уразливу гілку або стенд опубліковано у відкритому доступі.

## 10. Чекліст перед захистом

- [ ] Я перебуваю у правильній гілці.
- [ ] `git status` не показує незбережених потрібних змін.
- [ ] У репозиторії немає секретів і локальних даних.
- [ ] Я можу назвати vulnerable і fixed commit hashes, якщо робота містить дефект.
- [ ] Релевантні тести виконано після останньої зміни коду.
- [ ] Фінальний тег указує на виправлений commit.
- [ ] Гілку й тег надіслано до погодженого private remote.
- [ ] Я можу пояснити ключовий diff і виконати невелику live modification.
